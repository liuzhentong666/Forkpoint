# 本机维护恢复、权限与 Agent 实验记录

日期：2026-10-17。使用现有 Ubuntu WSL PostgreSQL 16.15，不启停或替换服务。自动化实验使用专用测试数据库；现有 `agentdb` 仅应用新增函数和授权的迁移，业务数据与版本历史不变。

**所有云存储仍未经真实验证，ECS 未部署。** 维护任务状态使用 MemoryStore；OSS 配置检查使用 SDK 测试替身。这里的本地报告不是正式管理任务的恢复存储，也不改变正式状态采用云对象存储的设计。没有运行 Claude。

## 1. 旧维护者醒来后必须收到冲突

用事件屏障固定顺序：A 发布意图并完成数据库快照，在发布完成状态前停顿；B 接手，检查快照已存在并发布完成状态；A 醒来，继续使用旧版本发布。

原实现捕获发布 Conflict 后，如果发现任务已经完成，就返回成功。新增测试在原实现上失败，证明它能发现这一问题。修复后，A 收到 Conflict，最终 head 保持 B 发布的版本，完成事件的 actor 为 B。

修复位于 `agent_state/maintenance.py`，只移除完成发布处吞掉冲突的处理。Engine 对相同命令和相同请求的网络重试仍返回原结果。本实验使用不同 actor；它不证明同一身份下的执行实例隔离，也不阻止旧执行者在其他系统产生副作用。head 的条件发布不是跨系统事务或通用 fencing。

## 2. 两个中断窗口均可接手

| 注入位置 | B 接手前的真实 PostgreSQL 状态 | B 的结果 |
|---|---|---|
| 意图已记录，数据库动作尚未发生 | 快照不存在 | 执行物化，核验成功，`applied=true` |
| 数据库已经提交，完成状态尚未发布 | 快照已存在 | 跳过物化，核验成功，`applied=false` |

新增 `after_intent` 注入点，保留原 `after_apply` 参数的位置以兼容调用方。中断由异常注入，接手方读取同一内存存储中的检查点；这验证控制流程和 PostgreSQL 状态探测，不是断电或云端持久性测试。上述两种情况和旧维护者场景均在真实本机 PostgreSQL、受限维护角色下再次通过。

## 3. 从配置入口检查 prefix

新测试使用 `review/nondefault` 前缀，经过 JSON 配置读取、存储工厂、维护 CLI 和服务启动装配。维护 CLI 写入的任务能被服务读取，默认前缀中找不到该任务。

这一检查在当前修复前的源码上已通过，**本次没有复现 prefix 错配，也没有声称修复了该缺陷**；新增覆盖用于阻止将来只在手动构造 Engine 时传递 prefix 的回归。OSS 客户端使用 FakeOSS，服务监听器被替换为测试对象，没有访问真实桶，也没有把此项当作完整 HTTP 联调。

## 4. 受限管理角色与十个分支全部合入

### 角色与迁移

新增 `sql/003_manager_role.sql` 与 `db.py install-manager`。`agentdb_manager` 是无登录、无超级用户权限的角色，业务能力仅为检查快照状态和调用既有物化函数。`vc.snapshot_status` 返回版本、逻辑表、快照是否存在，维护器无需直接读取历史表。函数固定 search_path，撤销 PUBLIC 执行权限。

真实 PostgreSQL 验证了允许的维护操作，并以 SQLSTATE `42501` 拒绝七类操作：直接读历史、改写历史、直接删除快照记录、修改业务表、创建版本、创建函数、创建角色。

角色测试使用可信管理员连接上的 `SET ROLE`。它验证数据库授权，**不代表持有管理员凭据的 Agent 已被隔离**；真正部署需独立受限登录身份。本次未创建登录密码。可修改系统规则的管理员仍保留，常规维护角色不取代它。

迁移在旧结构测试库 `agentdb_test_7a1b14ad0135` 和现有项目库 `agentdb` 各执行两次，确认可重复应用。前后商品、订单、分支摘要一致，changeset、行历史、文件历史、快照数量一致。原始记录见 [迁移结果](../manager-migration-results.json)。

### 全部合入实验

专用库：`agentdb_test_review_2a02f90171`。4,000 行商品，十个脚本写入者从同一基线分支，每人修改互不重叠的十行和一个代码文件，再并发合入同一个 main。它们是真实数据库连接，**不是十个大模型 Agent**。

| 指标 | 本次结果 |
|---|---:|
| 最终合入的分支 | 10 / 10 |
| 修改 / 保持原值的商品行数 | 100 / 3,900 |
| 最终保留的代码文件 | 10 |
| 创建分支时复制的行历史 | 0 |
| 分支准备与提交耗时 | 4,967.083 ms |
| 全部合入阶段耗时 | 9,467.149 ms |
| 端到端耗时 | 14,931.300 ms |
| 单个合入任务耗时中位数 / 最大值 | 6,967.983 / 9,461.335 ms |
| 陈旧 head 引发的重读重试 | 45 次 |

十个来源提交均可从最终 main 沿父边到达，固定基线仍保持原值，没有遗留工作事务。只有 `40001` 陈旧版本错误触发有界重读重试，语义冲突不会被盲目重试。

计时包含客户端、WSL/psql 启动、等待、重试和最终 COMMIT，不含测试库初始化、其他检查及末尾完整性核验。所有写者起初刻意竞争同一个 head；这是一次本机争用实验，不能推导生产吞吐或模型协作能力。45 次重试也提示后续应测量退避/合入调度的收益。原始结果见 [本机审查结果](../local-review-results.2026-10-17-spawn.json)（`local-review-results.json` 会被之后的运行覆盖）。耗时分解与后续建议见 [合入耗时分解](MERGE_BENCHMARK.md)。此后 `review_local.py` 的写入者默认复用长连接，复测结果也记录在该文档中。

## 5. 真实 GPT 实验

使用 `agent_lab.py` 和另一个专用库 `agentdb_test_gpt_70846a148f`。两个 GPT/Codex 子 Agent 从相同基线处理商品 101：一个调价 +10%，另一个库存 -5，同时各自提交对应 Python 规则。代码和行修改在同一 changeset 中；规则代码只保存并检查语法，不执行。

首次尝试因账户额度中断，留下一个库存提案和一个未写入的价格分支，main 未改变。用户继续后，两个真实 GPT 子 Agent 从已有状态恢复并完成实验；本次恢复没有再次遇到额度限制。它们继承当前会话模型，没有显式选择另一个具体版本。

| 实际步骤 | 结果 |
|---|---|
| 价格 Agent 读取基线、提交调价与代码 | 价格 10 → 11，库存仍为 100，合入成功 |
| 库存 Agent 用旧 expected 合入原提案 | `40001 / stale_head`，拒绝 |
| 重读当前 main 后，再检查旧库存提案能否合入 | `P0001 / merge_conflict`，商品 101 整行冲突 |
| 库存 Agent 从最新 main 建立恢复分支 | 重新表达库存 100 → 95，保留价格 11 |
| 检查差异、读取两份代码并合入 | 两份代码保留，最终价格 11、库存 95 |

原库存提案的整行状态包含价格 10，因此只更新 expected 无法解决语义冲突。GPT 根据错误重新建立提案，未将另一个 Agent 的价格修改覆盖回去。最终 main 为 `497b67f6-cbd5-4c01-981e-ab6241f16e4f`；独立核查确认总行数仍为 4,000，其余 3,999 行保持原值，固定基线未改变，两份被接受的提案均可从最终 main 到达，没有遗留工作事务。原库存提案仍由旧分支保留，没有删除历史。

实验发现并修正了一个客户端接口缺口：库存 Agent 只能通过 `info/diff` 看到文件哈希，无法在合入前核对代码正文。因此新增 `read-code --revision UUID --path ...`，允许按固定版本读取两种实验规则文件；已有库存提案与恢复提案均经此入口检查。最终核验检查 `PRICE = 11.0`、`STOCK = 95` 和真实行数据，不执行政策代码。

这是一项有明确目标、有限工具和协调者安排阶段的两 Agent 实验，不是自由探索盲测，也不代表十个模型并发或长期自主运行能力。数据库操作由 GPT 发起，数据库结果由协调者独立读取核对；中断前的部分操作通过数据库状态确认。结构化记录包含实际 Agent 报告的整理和独立数据库核验，不冒充完整原始工具轨迹。见 [GPT 实验记录](../gpt-agent-experiment.json)。

本次行为说明：客户端应同时提供固定版本、结构化冲突和按需读取代码的接口。只有“失败，请重试”不足以区分陈旧指针和需要重新表达意图的冲突；数据库端仍必须拒绝错误合入，不能依靠 Agent 自觉保持正确。

## 回归范围与复现

本次改动前原有 50 项状态/适配器/HTTP 本地测试通过。新增旧维护者测试在修复前失败，意图后中断测试在新增注入点前报错，配置前缀测试原本通过。修复后 **53 项全部通过**，保留原断言；专用 PostgreSQL 测试库中的原有 **18 项版本引擎断言通过**。

在项目目录使用原有本机连接配置执行：

```console
.\.venv-cloud\Scripts\python.exe -m unittest discover -s tests -v
.\.venv-cloud\Scripts\python.exe review_local.py
```

`review_local.py` 每次在同一个现有服务中新建专用测试数据库，并保留结果供核查。已有项目升级维护 API 使用 `python db.py install-manager`；新安装已包含这项迁移。GPT 实验入口说明见 `python agent_lab.py --help`，只有 `agentdb_test_gpt_<10位十六进制>` 库能作为工作目标；工具包装和 SET ROLE 都不是操作系统沙箱。

本次不更改持久对象编码。回退 Python 维护器不需要修改历史；新增角色和状态函数可保留。不要把回退理解为删除实验或正式历史。
